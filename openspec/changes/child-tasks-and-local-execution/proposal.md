## Why

The nodeagent is today only a *worker*: `Schedule` on its local schedulers is a reserved-but-unimplemented facet (`push` and `probe` both deliver errors), the node has no outbound facility, and no task can originate locally. Workflow-style handlers (e.g. a parent task that fans out to subtasks and aggregates their results) are impossible. Phase 4 of the pluggable-scheduling pipeline activates the node's `Schedule` facet: handlers spawn child tasks whose results return to the parent, whether the child runs on this node or is forwarded to a gateway. This makes the node a client as well as a worker, completing the scheduling contract (D1, archived `2026-08-30-pluggable-task-scheduling`) on the node side.

## What Changes

- **Node-side child-task submission** — the node's `Schedule` facet becomes real. A child task is routed through a per-type child router dispatching by `child.type()`; local scheduling authority is an explicit, opt-in role per scheduler entry — a `task_type` declaration (authoritative over that local type) and/or a single explicitly-marked `local_default` (the node's fallback authority for locally-originated tasks). Scheduler entries with neither role schedule no locally-originated tasks; empty `task_type` does NOT mean default (diverging from the gateway's `SchedulerConfig` semantics). Each authority-holding scheduler executes the policy *run locally if capacity allows, else forward to a gateway*. The child path is deliberately not probe-based (the parent is local; probing is pointless).
- **Task handlers do NOT evolve their interface** — `HandleTask(const Task&, ResultSenderPtr)` is unchanged (**locked decision**). The sender stays a per-call argument (it is per-task); the *submitter* is a shared node service and reaches only the handlers that need it, **at construction** through `NodeagentFactoryContext` — exactly how `RunTaskService`, `FunctionResolver`, `AdmissionController`, and `DataDependencyFetcherRouter` already reach extensions. `echo` and `piped_executable` never learn the submitter exists; `RunTask` stays byte-identical. A workflow handler's factory requests the submitter from the context and stores it in the handler. (Future per-submission hints — e.g. locality — are args on `Schedule`, not a different handle.)
- **Local receiver registry** (new, node-side) — `task.id → parent receiver`, the nodeagent mirror of `gateway::ResultReceiverStorage`. The parent registers a receiver keyed by the child's id before calling `Schedule(child, receiver)`. Inbound `kResult` and `kTaskRejected` frames on a node connection are recognized as child outcomes and delivered to the registry (today `NodeagentTlvHandler` drops both). Local execution delivers through a receiver-backed sender.
- **Local child run** — `RunTask` gains a sender-backed overload (no `Connection`), so a locally-admitted child runs with a sender that resolves through the local registry instead of a connection mailbox. `AdmissionTrackingSender` already wraps any `ResultSenderPtr`, so capacity accounting is unchanged.
- **Forward to a gateway** — new `GatewayClient` egress facility (enters `NodeagentFactoryContext`): forwards a child by submitting it upstream on a live gateway connection with a standard `kTaskSubmission` frame, falling back to a configured outbound dial when no live connection exists. **BREAKING config**: `NodeAgentConfig` gains a `gateway_client` section (gateway addresses + options); `schedulers` entries change shape to a node-side `NodeSchedulerConfig` (`extension`, optional `task_type` local authority, optional `local_default` marker), enabling per-type + default child routing.
- **Gateway inbound child handling** — the gateway treats an upstream `kTaskSubmission` from a node connection as a normal task through its per-type router (`GatewayTlvHandler`'s existing default seam → `SchedulerRouter::HandleFrame`, which now claims `kTaskSubmission`). A new node-connection result receiver (the TLV sibling of `HttpResultReceiver`) writes `kResult`/`kTaskRejected` frames back over the submitting node's live connection; the receiver is stored in the existing `ResultReceiverStorage` keyed by `node_id = submitting node`, so disconnect cleanup already works.
- **No wire-protocol change**: upstream children reuse the existing `kTaskSubmission`/`kResult`/`kTaskRejected` TLV framing; results are two-hop (child node → gateway → submitting node → parent).

## Capabilities

### New Capabilities
- `child-task-submission`: node-side submission handle injected into workflow task handlers at construction (not via `HandleTask`); the per-type child router; the run-locally-else-forward policy; the sender-backed `RunTask` overload for local children.
- `child-result-routing`: the two-hop result plumbing — the node-local receiver registry, inbound `kResult`/`kTaskRejected` delivery to parent receivers, and the gateway's node-connection result receiver.
- `gateway-client`: nodeagent egress — upstream submission on a live gateway connection, outbound dial fallback, connection lifecycle, and config.

### Modified Capabilities
- `node-local-scheduler`: the reserved "child-task `Schedule`" requirement is replaced by the real facet — node `Schedule` routes through the per-type child router and executes local-run-or-forward; drives the child-task `Schedule` seam from error-delivery to submission.
- `nodeagent-task-handlers`: `TaskHandler` factories MAY obtain a child-task submitter from `NodeagentFactoryContext` at construction; the `HandleTask` signature is unchanged; workflow handlers (first concrete consumer lands with an example extension) receive the submitter as a constructor dependency.
- `nodeagent-config`: `schedulers` entries gain a node-side `NodeSchedulerConfig` shape — optional `task_type` (local authority over a type) and an explicit `local_default` marker (the node's fallback authority, at most one; empty `task_type` is NOT a default) — plus a new `gateway_client` section for egress. Schema breaking.
- `pluggable-scheduler`: the gateway router claims inbound `kTaskSubmission` on node connections and routes it as a normal task through `Schedule`, completing the loop for forwarded children.

## Impact

- **No wire change**: `task-protocol` framing is unchanged (new usage of existing frame types).
- **Breaking config** (nodeagent): `schedulers` entry shape changes to `NodeSchedulerConfig` (`extension` + optional `task_type` + optional `local_default`); `gateway_client` section added. No legacy loading for the `schedulers` shape (mirrors gateway's Phase-0B breaking change).
- **Code**:
  - nodeagent: `src/nodeagent/core/{child_submission_router, local_receiver_registry, run_task_service}.hh`, `nodeagent_tlv_handler` (child-result routing), `extensions/schedulers/{push,probe}` `Schedule` facets, `exe/nodeagent_framework.cc` + `nodeagent_factory_context` (GatewayClient, child router, registry), new `extensions/task_handlers/` workflow example.
  - gateway: `src/gateway/core/{node_connection_result_receiver, scheduler_router, gateway_tlv_handler}`, `exe/gateway_framework.cc`.
  - config: `api/nodeagent/config/nodeagent.proto`.
- **Tests**: new tests for the child router, local registry, sender-backed `RunTask`, `GatewayClient`, upstream-submission routing, and the full two-hop result path; existing handler tests unchanged (evidence of zero interface churn).
